# payment-service

Оплата услуг по заявке: приём платежа (эквайринг/платёжная ссылка), статус оплаты, возвраты при
отмене заявки. См. раздел [3.2 spec.md](../../spec.md#32-payment-service--оплата-услуг).

Реализуется в рамках Фазы 9 (см. чек-лист в spec.md).

Пять слоёв по общему образцу монорепозитория: `PaymentService.Domain` / `.Application` /
`.Persistence` / `.Infrastructure` / `PaymentService` (API-хост). БД и пользователь Postgres —
`paymentservice`, порт для будущей записи в `docker-compose.yml` зарезервирован **8090**.

Сервис одновременно потребитель и издатель событий: подписывается на `OrderConfirmed` (выставление
счёта) и `OrderCancelled` (возврат), публикует `PaymentCompleted`, `PaymentFailed`, `RefundIssued`, —
поэтому у него будут и consumer с inbox, и транзакционный outbox (как у document-service).

Деньгами распоряжается внешний платёжный провайдер; у себя сервис хранит счета, платежи и их
статусы, а также идентификаторы транзакций провайдера — по ним сопоставляются входящие webhook.

## Счета и платежи

`Invoice` — счёт по подтверждённой заявке (одна заявка — один счёт, уникальность в схеме),
`Payment` — одна попытка его оплаты; попыток может быть несколько, и они часть агрегата счёта.
Консьюмер `OrderConfirmed` (очередь `payment-service.order-confirmed` + DLQ) выставляет счёт и
сразу заводит платёж у провайдера, получая платёжную ссылку. Повторные доставки отсекает inbox
по `EventId`, а повторное выставление счёта — проверка «счёт по заявке уже есть» и уникальный
индекс.

Переход счёта в `Paid` происходит по уведомлению провайдера (см. ниже): при redirect-схеме
свежесозданный платёж всегда ждёт оплаты.

## Webhook провайдера

`POST /api/payments/webhook` — единственный эндпоинт сервиса, анонимный: стучится сюда чужой
сервер, токена Keycloak у него нет. Защита не в аутентификации запроса, а в том, что **его телу
не верят**: при подключённом провайдере статус платежа перечитывается прямым запросом к нему,
и знание идентификатора платежа само по себе не даёт объявить заявку оплаченной. На стенде с
песочницей перепроверять не у кого, поэтому тело принимается как есть — и это записывается в лог
предупреждением.

Коды ответа выбраны под то, что провайдер повторяет доставку на любой не-2xx:

| Ситуация | Ответ |
|---|---|
| исход записан, уже записан ранее, платёж ещё ждёт оплаты, платёж не наш | `200` — повтор ничего не изменит |
| провайдер недоступен для перепроверки | `503` — просим прислать уведомление снова |
| тело не разбирается | `400` |

Успех переводит платёж в `Succeeded`, счёт — в `Paid` и ставит в outbox `PaymentCompleted`;
отмена переводит платёж в `Failed`, оставляя счёт `Issued` (неудачная попытка не отменяет
обязательство — клиент вправе оплатить снова), и ставит `PaymentFailed`. Событие и изменение
статусов коммитятся одной транзакцией, публикует их `OutboxDispatcher` раз в 5 секунд.

## Возвраты

Consumer `OrderCancelled` (очередь `payment-service.order-cancelled` + DLQ) закрывает денежную
сторону отменённой заявки:

| Состояние счёта | Что происходит |
|---|---|
| счёта нет (отмена до подтверждения) | ничего |
| `Issued`, оплаты не было | счёт → `Cancelled`, возврата нет |
| `Paid` | возврат у провайдера, счёт → `Refunded`, публикуется `RefundIssued` |
| `Cancelled` / `Refunded` | идемпотентный no-op |

`Refund` — отдельная сущность, а не статус платежа: это самостоятельная транзакция у провайдера
со своим идентификатором и исходом, и сумма у неё своя (возврат бывает частичным).

Незавершённые платежи при отмене намеренно не трогаются — платёжная ссылка живёт у провайдера, и
клиент всё ещё может по ней заплатить. Такая **поздняя оплата** обрабатывается явно: если счёт
уже `Cancelled`, webhook записывает платёж успешным и тут же отправляет его на возврат, а
`PaymentCompleted` не публикует — заявка отменена, наружу уходит только `RefundIssued`.

Отказ провайдера в возврате оставляет счёт `Paid`, а возврат — `Failed`: деньги всё ещё у
платформы, и объявлять их возвращёнными нельзя. Автоматических повторов нет.

## Платёжный провайдер

Эквайринг спрятан за `IPaymentProviderClient` (Application): создать платёж и получить платёжную
ссылку, спросить статус, вернуть деньги. Карточные данные через сервис не проходят — плательщик
вводит их на стороне провайдера, куда его уводит `confirmationUrl`.

Реализаций две, выбор — по наличию учётных данных магазина в секции `PaymentProvider`:

| Настройки | Клиент | Поведение |
|---|---|---|
| `ShopId` + `SecretKey` заданы | `YooKassaPaymentProviderClient` | REST API провайдера (контракт ЮKassa), Basic-аутентификация, `Idempotence-Key`, Polly retry/circuit breaker/timeout |
| не заданы (по умолчанию) | `SandboxPaymentProviderClient` | платежи заводятся в памяти процесса и остаются `Pending`; ссылка никуда не ведёт |

Песочница сознательно **не** проводит платёж сама: довести его до оплаты на стенде можно так же,
как это сделал бы провайдер, — постучав в webhook сервиса. Повтор с тем же ключом идемпотентности
возвращает тот же платёж, поэтому защиту от повторной обработки события можно проверять и на ней.

```json
"PaymentProvider": {
  "BaseUrl": "https://api.yookassa.ru/v3",
  "ShopId": null,
  "SecretKey": null,
  "Currency": "RUB",
  "ReturnUrl": "http://localhost:8090/api/payments/return"
}
```

`ReturnUrl` — адрес, куда провайдер возвращает плательщика после оплаты; в боевой конфигурации это
страница витрины, значение по умолчанию — заглушка для локального стенда.

## Команды

```
dotnet build PaymentService.slnx
dotnet run --project PaymentService
```

Миграции (из `PaymentService.Persistence/`):

```
dotnet ef migrations add <Name>
dotnet ef database update
```

Тесты:

```
dotnet test PaymentService.Application.Tests
dotnet test PaymentService.IntegrationTests
```

`PaymentService.Application.Tests` — xUnit + Moq, без внешних зависимостей: провайдер везде мок.
`PaymentService.IntegrationTests` — xUnit + `Mvc.Testing` + Testcontainers, нужен запущенный
Docker-демон; RabbitMQ и провайдер не поднимаются (все `IHostedService` сняты, клиент провайдера
заменён управляемой заглушкой), а учётные данные магазина в настройках заданы намеренно — именно
они включают перепроверку webhook, то есть боевое поведение.

В общем стеке сервис поднимается вместе с остальными (`docker compose up --build` из корня
репозитория) на порту **8090**.
